## 2. 背景与审查基线

当前 EXE 可以启动，窗口可响应，拖拽组件能够加载，中文及空格路径能够完成基本处理。现有源码测试基线为 `390 passed, 3 skipped`，Ruff 通过。EXE 为 x64，并启用了 ASLR、High-Entropy VA 和 DEP；这些能力不得回退。

当前发布 EXE 的 SHA-256 为：

```text
F798BDB503F265E707AA57270545B0917348466E38DC367A02A41B7BCA4F3A85
```

已验证存在以下缺陷：

| ID | 优先级 | 缺陷 | 用户影响 |
| --- | --- | --- | --- |
| BUG-01 | P0 | GIF、APNG、动画 WebP、多页 TIFF 被静默处理为单帧 | 不可恢复地丢失其余帧，界面仍报告成功 |
| BUG-02 | P0 | BMP、GIF、TIFF 输出可能写成 PNG 内容但保留原扩展名 | 文件格式与扩展名不一致，其他软件可能无法打开或错误识别 |
| BUG-03 | P0 | 后台线程为 daemon，输出直接写最终路径 | 关闭窗口可能终止写入并留下半文件 |
| BUG-04 | P0 | `_clean` 到 `_clean_999` 都存在时回退到 `_clean_final` | 已存在的 `_clean_final` 会被覆盖 |
| BUG-05 | P1 | 检测与移除使用不同的 EXIF Orientation 像素方向 | 检测位置和实际移除位置可能不一致，输出显示方向可能改变 |
| BUG-06 | P1 | 元数据清理路径会丢失普通 EXIF、Author、Title、Artist、ICC 或 DPI | 清理 AI 标记时破坏用户原始信息 |
| BUG-07 | P1 | 同一图片先显示“无法判定”，随后又报告移除了 Gemini 水印 | 检测报告与处理结果互相矛盾，结果不可信 |
| BUG-08 | P1 | 通过日志文本是否包含“失败”判断状态，批处理总是显示“完成 N 张” | 失败、警告和成功统计不真实 |
| BUG-09 | P1 | 文件夹递归扫描在 UI 线程执行 | 大目录会冻结窗口 |
| BUG-10 | P1 | 扫描会把后缀为 `.png` 的目录当文件，并排除合法 `*_clean.png` 输入 | 队列中出现伪文件，合法用户文件无法处理 |
| BUG-11 | P2 | EXE 依赖与 `uv.lock` 漂移，构建命令不冻结环境 | 同一源码无法稳定重建同一依赖集合 |
| BUG-12 | P2 | EXE 无版本资源、无 Authenticode 签名，发布包缺项目 LICENSE 和完整第三方声明 | Windows 信任度低，版本和许可证不可审计 |
| BUG-13 | P1 | GUI 未进入正式 Pyright 门禁，单独检查存在 17 项错误 | GUI 回归不能被当前质量门禁及时发现 |

已观察到的依赖漂移包括：

| 依赖 | 当前 EXE | 当前锁文件 |
| --- | --- | --- |
| `c2pa-python` | `0.37.6` | `0.37.2` |
| OpenCV | `5.0.0.93` | `4.11.0.86` |
| NumPy | `2.5.2` | `1.26.4` |
| PyWavelets | `1.8.0` | Python 3.12 解析为 `1.9.0` |

这些版本只用于证明当前构建漂移，不代表目标版本。目标版本必须由更新后的 `uv.lock` 唯一决定。

## 3. 目标

1. 不再发生静默丢帧、格式伪装、已有文件覆盖和中断半文件。
2. 检测、可见水印定位和移除使用同一份、同一方向的像素数据。
3. 仅剥离 AI 相关元数据；容器支持的普通元数据必须保留。
4. 每个文件和整个批次都给出结构化、真实、可测试的结果。
5. 文件夹扫描和处理均不阻塞 Tk 主线程，关闭窗口时安全完成当前文件后退出。
6. 从锁文件可重复解析构建环境，并生成可审计、可签名的正式发布包。

## 4. 非目标

1. 本期不实现 GIF、APNG、动画 WebP 或多页 TIFF 的逐帧水印处理与动画重新编码。
2. 本期不新增输出格式转换功能；输出格式必须与输入格式一致。
3. 本期不增加强制终止当前图片的硬取消。关闭时只在当前文件完成后停止批次。
4. 不更改水印算法阈值来掩盖报告与移除不一致；应消除重复解码或重复判定的真相源。
5. 不引入数据库、任务框架或新的 GUI 框架。
6. 不使用自签名证书冒充正式 Authenticode 签名。

## 5. 产品行为契约

### 5.1 输入格式准入

GUI 第一阶段只接受以下静态图片：

| 实际格式 | 允许扩展名 | 附加条件 |
| --- | --- | --- |
| PNG | `.png` | `n_frames == 1`；APNG 必须拒绝 |
| JPEG | `.jpg`、`.jpeg` | 单图 |
| WebP | `.webp` | `n_frames == 1` 且非动画 |
| AVIF | `.avif` | `n_frames == 1` 且当前打包解码器可完整读取 |
| BMP | `.bmp` | 单图 |
| TIFF | `.tif`、`.tiff` | `n_frames == 1` |

GIF 无论单帧还是动画，本期均不支持。原因是当前写入链路不能可靠保证 GIF 容器和调色板语义，不允许继续把 GIF 当成静态普通图片处理。

处理前必须完成预检：

1. 路径存在、是普通文件且可读。
2. 根据文件头/解码器获得实际格式，不只相信扩展名。
3. 实际格式必须与扩展名映射一致；例如 PNG 内容命名为 `.bmp` 必须拒绝。
4. 检查 `n_frames`/动画属性；多帧输入必须拒绝。
5. 图片必须能完成实际解码，不得只成功读取文件头。

预检失败时：

- 该文件状态为“失败”，错误阶段为 `input`；
- 日志使用明确中文原因，例如“暂不支持动画 WebP，共 12 帧”；
- 不创建最终输出、占位输出或零字节输出；
- 批次继续处理后续文件。

### 5.2 单一方向与像素真相源

只要请求包含像素检测或可见水印移除，就必须执行一次统一解码：

1. 读取原始像素和 alpha。
2. 按 EXIF Orientation 转换为用户看到的显示方向。
3. 报告中的可见水印检测、可见水印定位和实际移除全部使用这同一份归一化像素。
4. 不允许 `identify()` 再按另一组 OpenCV flags 独立解码同一文件并决定可见水印结论。
5. 输出已经物理旋转时，EXIF Orientation 必须删除或写为 `1`，防止查看器二次旋转。
6. 除 Orientation 的必要归一化外，其他受保护元数据必须保持不变。

元数据证据仍从原始文件字节读取；“共用像素”不等于放弃 C2PA、EXIF、XMP 等文件级证据。仅选择“剥离 AI 元数据”且没有任何像素阶段时，应保持原始像素方向和合法 Orientation，不应为了清理元数据额外重编码或旋转图片。

报告和移除不得出现两个独立的可见水印判定结果。若同一次处理实际移除了 `gemini`，该次报告必须包含对应可见标记，最终判定不能仍显示“无法判定”。“未检测到可见水印”是正常成功结果，不是异常。

### 5.3 普通元数据保护

清理目标是 AI 相关 C2PA、EXIF/XMP/IPTC 标记和已定义的 AI 文本字段，不是清空全部元数据。

以下数据在输入容器支持且原文件包含时必须保留：

- 普通 EXIF：相机厂商/型号、拍摄时间、曝光信息、GPS、Artist 等；
- 标准文本：Author、Title、Description、Copyright、Comment 等；
- ICC 色彩配置；
- DPI/分辨率信息；
- 透明通道；
- 与 AI 来源无关的普通编辑器信息。

实现必须在处理前保存受保护元数据快照，并在临时输出上做等价性校验。允许的差异只有：

- 明确命中的 AI 字段被删除；
- 像素已按 Orientation 物理归一化时，Orientation 变为 `1` 或不存在；
- 编码库进行的无语义类型规范化，例如等价的有理数表示。

若某个恢复/规范化分支无法同时清理 AI 标记并保留受保护元数据，必须返回失败且不发布最终文件。禁止继续沿用“清理失败后重写整个栅格并静默丢掉普通元数据”的成功路径。

### 5.4 输出格式与完整性

输出必须保持输入的实际容器格式和合法扩展名：

- PNG 输入生成 PNG；
- JPEG 输入生成 JPEG；
- 静态 WebP 输入生成 WebP；
- AVIF 输入生成 AVIF；
- BMP 输入生成 BMP；
- 单页 TIFF 输入生成 TIFF。

不能通过把所有未知格式默认保存为 PNG 来“保证能写”。每次发布前必须重新读取临时输出并验证：

1. 文件非空且能完整解码；
2. 魔数/实际格式与目标扩展名一致；
3. 帧数仍为 1；
4. 尺寸符合预期；若 Orientation 为 5-8，允许归一化导致宽高交换；
5. alpha 在支持透明度的格式中保留；
6. AI 元数据复扫为空；
7. 受保护元数据满足 5.3 的约束。

任一验证失败都不得发布最终文件。

### 5.5 原子写入与永不覆盖

所有会产生输出的处理必须使用同目录事务式写入：

1. 在最终输出所在目录创建独占临时文件，临时文件后缀必须与最终格式一致。
2. 所有可见水印处理、元数据清理和验收都针对临时文件完成。
3. 最终文件名必须通过排他方式预留，不能只用 `Path.exists()` 做存在性判断。
4. 全部验证通过后，才用同卷原子替换把临时文件发布到本进程拥有的预留路径。
5. 受控失败或取消时清理临时文件和本进程创建的占位；绝不删除用户原有文件。

命名规则保持：

```text
photo_clean.png
photo_clean_1.png
photo_clean_2.png
...
photo_clean_1000.png
...
```

编号不得限制为 999，不再使用 `_clean_final` 回退。无论目录中预先存在多少个同名输出，都必须选择新的独占名称，且任何已有文件的字节和修改时间都不得改变。

可见水印阶段失败时，不能留下“已生成但可能仍含 AI 元数据”的最终文件。只有完整处理和验证通过的结果才对用户可见。

### 5.6 结构化结果与批次统计

禁止再通过 `"失败" in result` 或其他日志文本推断状态。至少建立以下结构化语义：

```python
FileStatus = Literal["success", "warning", "failed", "cancelled"]

@dataclass(frozen=True)
class FileProcessResult:
    source: Path
    status: FileStatus
    output: Path | None
    messages: tuple[str, ...]
    error_stage: str | None
    error: str | None
```

字段名可以根据现有代码风格微调，但必须满足同等信息量，且 UI、`--selftest` 和批次汇总只读取结构化字段。

状态规则：

| 场景 | 状态 |
| --- | --- |
| 所有请求的关键阶段成功 | `success` |
| 处理成功，但可选的处理前报告失败 | `warning` |
| 只请求报告且报告失败 | `failed` |
| 输入不支持、读取失败、可见处理失败、元数据残留、写入/验证/发布失败 | `failed` |
| 无法判定图片来源 | 正常报告结果，不是失败 |
| 未检测到可见水印 | 正常处理结果，不是失败 |
| 用户关闭后尚未开始的文件 | `cancelled` |

批次结束状态必须显示真实统计：

```text
处理结束：成功 7，警告 1，失败 2，取消 3
```

Treeview 每行状态必须来自对应 `FileProcessResult`。`--selftest` 在 `success`/`warning` 时返回 0，在 `failed` 时返回非 0；不得扫描中文日志决定退出码。

### 5.7 后台扫描与路径处理

文件夹递归扫描必须移出 Tk 主线程。扫描期间窗口仍应响应重绘、拖动和关闭事件；后台线程不得直接操作 Tk 控件，只能通过线程安全队列把结果交回主线程。

路径规则：

1. 文件夹枚举结果和直接输入都必须通过 `is_file()`；后缀为 `.png` 的目录不能进入文件队列。
2. 拖拽数据使用 Tk 原生 `root.tk.splitlist(event.data)` 解析，不再使用正则拆路径。
3. 使用规范化绝对路径作为去重键；Windows 上必须按大小写不敏感语义去重。
4. 保持稳定顺序：顶层输入顺序优先，单个目录内按规范化路径排序。
5. 不得根据 `_clean` 文件名或父目录名排除输入。`portrait_clean.png` 可能是合法原图。
6. 无权限目录、失效链接或扫描中的单项错误应记录为明确警告，不能让整个 GUI 崩溃。
7. 初始命令行路径也必须走同一后台扫描和去重逻辑。

### 5.8 关闭与取消语义

处理线程必须改为非 daemon，并保存线程引用。窗口注册 `WM_DELETE_WINDOW`：

1. 空闲时立即正常退出。
2. 批次运行时设置线程安全的停止事件，状态显示“正在完成当前文件后退出”。
3. 当前文件继续完成原子处理；工作线程在文件边界检查停止事件，不再开始下一张。
4. 未开始的队列项标记为 `cancelled`。
5. 工作线程结束并发送最终汇总后，Tk 主线程才销毁窗口。
6. 工作线程不得调用 Tk API；窗口销毁后不得继续安排 `after()` 回调。

本期不要求中断正在执行的 OpenCV 操作。任务管理器强杀、断电等不可控终止可能留下临时文件，但不能出现指向最终名称的半成品。

### 5.9 可复现构建

必须把 GUI 构建依赖纳入项目依赖和 `uv.lock`，至少包括：

- PyInstaller；
- `tkinterdnd2`；
- GUI 实际使用的 Pillow、piexif、C2PA、NumPy、OpenCV、PyWavelets 等运行依赖。

要求：

1. 在 `pyproject.toml` 中建立清晰的 GUI 运行/构建 extra，具体名称可按项目规范确定。
2. 更新并提交 `uv.lock`，所有构建都从该锁文件解析。
3. 正式构建命令必须包含 `--frozen`；锁文件与项目声明不一致时立即失败。
4. `scripts/build_gui.spec` 仍从当前工作树 `src/` 收集代码，不得混入全局安装的另一版本包。
5. 构建后生成依赖清单，记录包名、版本、许可证、Python 版本、目标架构和构建时间。
6. 在干净环境连续构建两次时，解析到的包版本和依赖清单必须一致；本期不要求 PyInstaller 二进制逐字节可复现。
7. 构建验收必须检查 EXE 内实际版本，不能只读取构建环境的 `pip list`。

推荐唯一正式入口（onedir 文件夹发布）：

```powershell
uv run --frozen --extra <gui-build-extra> pyinstaller --clean --noconfirm --distpath release-onefile --workpath build-tmp-onedir scripts/build_gui.spec
```

（原 one-file 单 exe 发布因每次启动都要向 `%TEMP%` 解压约 227MB，
实测首窗口出现需 30 秒以上，故降级为备选：`scripts/build_gui_onefile.spec`。）

发布脚本（生成标注/签名、打包 zip、写 SHA256SUMS）：
```powershell
./scripts/publish_gui.ps1 -AllowUnsigned   # 开发包
./scripts/publish_gui.ps1 -Signed          # 正式（需 $env:SIGNCERT_THUMBPRINT）
```

若增加封装脚本，该脚本仍必须执行等价的冻结检查，且任一步失败都返回非 0。

### 5.10 发布身份、许可证与签名

正式发布包必须包含（onedir 文件夹发布，exe 与清单文件位于同一文件夹内）：

```text
印消/
  印消.exe
  _internal/            # Python 运行时 + 依赖（onedir 形态，无逐次解压）
  LICENSE
  THIRD_PARTY_NOTICES.txt
  DEPENDENCIES.txt
  SHA256SUMS.txt
  UNSIGNED-DEV-BUILD.txt   # 仅未签名开发包
```

（onedir 形态启动秒开：运行时与依赖常驻 `_internal/`，不向 `%TEMP%` 解压。
C2PA native 库 `c2pa_c.dll` 必须显式打包进 `_internal/c2pa/libs/`，避免 C2PA
检测在分发版中静默缺失。）

要求：

1. EXE 写入 Windows 版本资源。`FileVersion`、`ProductVersion` 必须从项目版本单一生成，不手工维护第二份版本号。
2. 版本资源至少包含 ProductName、FileDescription、FileVersion、ProductVersion、OriginalFilename 和合法 Copyright。
3. 根项目 Apache-2.0 `LICENSE` 必须复制到发布包。
4. `THIRD_PARTY_NOTICES.txt` 必须覆盖实际打入包内的第三方组件及许可证，不只列顶层 Python 包。
5. `SHA256SUMS.txt` 至少记录 EXE 和最终发布压缩包哈希。
6. 提供使用 SHA-256 和可信时间戳服务的 Authenticode 签名步骤；证书和密码只从安全环境注入，禁止写入仓库。
7. “正式发布”任务在无证书或签名验证失败时必须失败。允许单独生成明确标注的开发测试包，但不能将其报告为已签名正式版。
8. 发布后使用 `Get-AuthenticodeSignature` 验证状态为 `Valid`，并复核 x64、ASLR、High-Entropy VA 和 DEP 没有回退。

## 6. 建议代码边界

优先在现有模块内做最小正确修改，不为本 PRD 引入新的框架。

| 文件 | 预期职责 |
| --- | --- |
| `scripts/gui_app.py` | 输入预检编排、后台扫描、结构化结果、批次统计、关闭协议、输出命名与事务发布 |
| `src/remove_ai_watermarks/image_io.py` | 统一 EXIF 方向解码、格式一致的读写、alpha 处理；避免多处各自实现 |
| `src/remove_ai_watermarks/identify.py` | 允许 GUI 的可见检测复用已归一化像素/检测结果，同时保留原始文件元数据证据 |
| `src/remove_ai_watermarks/api.py` | 可见水印移除复用同一像素表示；写入失败继续显式抛错 |
| `src/remove_ai_watermarks/metadata.py` | 同格式写回、普通元数据保存与验证，禁止丢元数据的静默恢复成功 |
| `scripts/build_gui.spec` | 锁定后的依赖收集、版本资源、发布文件 |
| `pyproject.toml` / `uv.lock` | GUI 运行和构建依赖的唯一解析来源 |
| `tests/test_gui_app.py` | GUI 纯逻辑、线程协议、命名和批次状态测试 |
| 现有 image/API/metadata 测试 | 方向、格式和元数据回归测试 |

如果为了共用像素而调整公共 Python API，必须保持现有调用兼容；优先增加可选关键字参数或内部入口，不要破坏现有位置参数和返回类型。

## 7. 实施顺序

### 阶段 A：先建立失败测试

1. 为 BUG-01 至 BUG-10 添加最小回归测试，确认测试在旧实现上能稳定复现。
2. 为 Orientation=6、普通 EXIF/文本/ICC/DPI 构造确定性夹具。
3. 为 BMP、TIFF 和扩展名伪装构造魔数断言。
4. 为 `_clean` 冲突超过 1000、并发占名和用户已有文件哈希构造测试。

### 阶段 B：修正输入、结果和扫描

1. 实现静态格式预检和多帧拒绝。
2. 用结构化 `FileProcessResult` 替换日志文本判定。
3. 修复路径解析、去重和 `_clean` 误过滤。
4. 将递归扫描移到后台线程。

### 阶段 C：修正图片事务链路

1. 建立一次性方向归一化和共享像素路径。
2. 统一报告与移除的可见标记事实。
3. 完成各静态格式的同格式输出。
4. 保存并复核受保护元数据。
5. 引入独占命名、同目录临时文件和原子发布。

### 阶段 D：修正生命周期

1. 非 daemon 工作线程、停止事件和线程引用。
2. 实现关闭窗口时“完成当前文件后退出”。
3. 正确标记未开始项并输出真实批次汇总。

### 阶段 E：收口构建和发布

1. 锁定 GUI 依赖并修复全部 GUI Pyright 错误。
2. 增加版本资源、依赖/许可证清单和哈希产物。
3. 增加正式签名入口和签名验证。
4. 从干净环境重建真实 EXE，执行完整验收矩阵。

每个阶段完成后先运行针对性测试，再进入下一阶段。不要等到最后才第一次构建 EXE。

## 8. 自动化测试要求

### 8.1 格式矩阵

| 用例 | 预期 |
| --- | --- |
| 静态 PNG/JPEG/WebP/AVIF/BMP/TIFF | 成功，输出实际格式与扩展名一致 |
| 单帧 TIFF | 成功且仍为单页 TIFF |
| GIF | 明确失败，无输出 |
| APNG | 明确失败并报告帧数，无输出 |
| 动画 WebP | 明确失败并报告帧数，无输出 |
| 多页 TIFF | 明确失败并报告页数，无输出 |
| PNG 内容改名 `.bmp` | 明确失败，无输出 |
| 截断/损坏图片 | 明确失败，无复制穿透的“成功”输出 |

### 8.2 Orientation 与元数据矩阵

至少构造 Orientation `1`、`3`、`6`、`8` 的 JPEG。Orientation=6 用例必须同时带有：

- Make、Model、DateTimeOriginal；
- Artist；
- Author、Title；
- ICC profile；
- DPI；
- 一个可移除的 AI 元数据标记；
- 一个位于显示方向确定坐标的可见标记夹具。

断言：报告和移除命中同一标记；输出视觉方向正确；Orientation 为 `1` 或缺失；除 AI 字段和 Orientation 规范化外，所有受保护元数据等价。

还需覆盖 PNG、WebP、AVIF、BMP、TIFF 各自可表达的标准元数据。若编码库确实无法无损表达某字段，测试预期应是显式失败且不发布，而不是静默成功。

### 8.3 原子性与覆盖保护

1. 预建 `_clean`、`_clean_1` 至 `_clean_1005` 及 `_clean_final`，确认选择 `_clean_1006` 或更高的新名字。
2. 记录所有已有文件的 SHA-256 和修改时间，处理后必须完全不变。
3. 在写入、元数据清理、复扫和发布各阶段注入异常，最终路径均不能出现半文件。
4. 两个线程同时为同一源文件申请输出名，必须获得不同路径。
5. 临时输出验证失败时不得覆盖预留路径以外的任何文件。

### 8.4 批次和关闭

1. 构造成功、警告、失败混合批次，断言 Treeview 状态与汇总数字一致。
2. 日志中包含“失败”二字但结构化状态为成功的测试，确认状态不受文本影响。
3. 处理第 1 张时触发关闭，确认第 1 张完整结束，第 2 张及以后为 `cancelled`。
4. 关闭过程中最终文件要么不存在，要么可完整解码并通过全部验证，不能为半文件。
5. 线程退出后不再调用 Tk `after()`，进程能够自然结束。

### 8.5 扫描

1. 包含中文、空格、花括号的拖拽路径能正确拆分。
2. 同一文件以相对路径、绝对路径和大小写变体添加时只出现一次。
3. `album.png/` 目录本身不进入队列，其内部合法图片正常进入。
4. `portrait_clean.png` 和位于 `exports_clean/` 下的合法原图正常进入。
5. 扫描大目录时用 Tk 心跳/测试替身证明主线程持续处理事件。

## 9. 质量门禁与验收命令

以下命令必须在更新后的锁文件和干净构建环境中通过。若项目最终采用不同 extra 名称，只替换占位名称，不得删除 `--frozen`。

```powershell
uv run --frozen pytest
uv run --frozen ruff check .
uv run --frozen pyright src tests scripts/gui_app.py
uv run --frozen --extra <gui-build-extra> pyinstaller --clean --noconfirm --distpath release-onefile --workpath build-tmp-onedir scripts/build_gui.spec
```

真实 EXE 还必须完成：

1. 对 8.1 和 8.2 矩阵执行 `--selftest` 或等价自动化入口。
2. 在中文和空格目录下运行。
3. 实际启动 GUI，添加文件、拖拽文件夹、运行混合成功/失败批次并关闭窗口。
4. 校验 EXE 内依赖版本与 `DEPENDENCIES.txt`、`uv.lock` 一致。
5. 校验 EXE 版本资源与 `pyproject.toml` 一致。
6. 校验发布包 LICENSE、第三方声明和哈希齐全。
7. 正式版校验 Authenticode 状态为 `Valid`。
8. 复核二进制仍为 x64，并启用 ASLR、High-Entropy VA、DEP。

不得只运行源码单元测试后宣称 EXE 已修复。真实打包运行是发布阻断门禁。

## 10. 完成定义

只有同时满足以下条件才可标记完成：

- BUG-01 至 BUG-13 均有对应自动化回归测试；
- 所有 P0/P1 用例通过，且没有通过降低断言或吞异常绕过；
- 原有测试无回归，Ruff 和包含 GUI 的 Pyright 全通过；
- 真实 EXE 格式、Orientation、元数据、覆盖、关闭中断和批次统计验收通过；
- 构建依赖与锁文件一致；
- 新发布包具备版本、许可证、依赖清单和哈希；
- 正式发布包已完成有效签名，或明确只产出未签名开发包且没有冒充正式版；
- 提供最终测试日志、新 EXE SHA-256、签名状态和仍存在的非阻断风险。

## 11. 回滚方案

1. 新构建输出到新的版本目录，不在验证前覆盖当前 `release/RemoveAIWatermarks`。
2. 保存当前发布包及其 SHA-256，作为只读回滚基线。
3. 任一格式数据损坏、已有文件覆盖、元数据异常丢失或签名失败都阻断发布。
4. 回滚只切换完整发布目录/压缩包，不从新旧版本中混拷 `_internal` DLL 或 Python 包。
5. 回滚后重新校验 EXE 哈希，确保确实恢复到已知基线。
